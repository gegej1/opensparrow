# Pruning Checklist

## 1. 目的
这份清单用于把统一总框架里的重复定义逐步剪掉，避免以下问题：

- 同一个事实被多处维护
- 同一类任务被多个系统重复拆分
- 同一个项目里出现多套“宪法”
- Agent 不知道该听谁的
- 新项目接入时背上过多历史包袱

本清单不直接替代架构文档，而是把 `01-Unified-Framework-Architecture.md` 中的原则转成具体的修剪动作。

---

## 2. 使用方式
每次准备整合或迁移某个框架模块时，按以下顺序检查：

1. 先判断这项内容属于哪一层
2. 确认该层是否拥有最终职责
3. 如果不是，就决定：删除 / 迁移 / 改成引用
4. 只有最终职责层可以保留“主定义”
5. 其他层只能：
   - 引用
   - 消费
   - 补充局部上下文
   - 不能重复定义全局规则

---

## 3. 四类处理动作

### A. 保留（Keep）
该内容属于本层的唯一职责，且当前存在形式合理。

### B. 迁移（Move）
该内容有价值，但放错了层，应该迁移到更合适的模块。

### C. 改写为引用（Reference）
该内容不应该在本层重复维护，但本层仍需要知道它存在。此时应改为：
- “遵循项目规范”
- “读取 longterm 事实源”
- “根据 spec 验收”

### D. 删除（Delete）
该内容重复且没有独立价值，应直接删除。

---

## 4. 模块级剪枝清单

## 4.1 Execution Layer（`superpower skill`）

### 应保留
- 会话级行为模式
- 调试、规划、验证、执行纪律
- “没有验证证据不能宣布完成”这类执行原则
- 当前回合如何推进任务的方法

### 应迁出 / 不应继续扩大
- 项目长期状态记录
- 项目 feature backlog
- 项目级代码风格与禁改区定义
- 项目级目录说明
- 项目长期 ownership 规则

### 修剪动作
- [ ] 检查 skill 文本中是否出现“项目级代码风格定义”
- [ ] 如果有，将其迁移或改写为“遵循项目 AGENTS / constitution”
- [ ] 检查 skill 是否试图维护长期 backlog 或 progress 逻辑
- [ ] 如果有，将其改写为“读取 longterm 项目事实源”
- [ ] 保留 skill 的“行为方法”，删除它对“项目事实”的重复叙述

### 剪枝后目标
`skill` 只告诉 Agent **如何工作**，不再告诉 Agent **项目长期事实本身是什么**。

---

## 4.2 Feature Delivery Layer（`spec规范`）

### 应保留
- `spec -> plan -> tasks`
- feature 范围、边界、验收标准
- feature 级执行方案
- feature 级任务拆分

### 应迁出 / 不应继续扩大
- 整个项目的 feature 全景
- 整个项目的长期进度记录
- 多 Agent 的长期编队制度
- 项目长期上下文数据库

### 修剪动作
- [ ] 检查模板和说明文档中是否把 `spec` 写成“整个项目管理系统”
- [ ] 如果有，把项目级状态说明迁回 `longterm`
- [ ] 检查 `spec` 模板里是否重复定义项目宪法
- [ ] 如果有，改写为“引用项目 AGENTS / constitution”
- [ ] 检查 `tasks` 是否承担跨 feature 的 backlog 选择职责
- [ ] 如果有，迁回 `longterm` 的 feature 选择机制

### 剪枝后目标
`spec规范` 只负责把**一个 feature**交付出来，不再承担整个项目的长期管理。

---

## 4.3 Project Memory Layer（`longterm`）

### 应保留
- `app_spec`
- `feature_list`
- `progress`
- `init`
- session 合同
- 跨会话项目事实

### 应迁出 / 不应继续扩大
- 单个 feature 的细任务拆分
- 多 Agent ownership 分配规则
- 会话级执行技能
- 项目特定代码风格的二次定义

### 修剪动作
- [ ] 检查 `longterm` 文档是否过多介入 `spec -> plan -> tasks` 的细节
- [ ] 如果有，把 feature 级细拆职责还给 `spec规范`
- [ ] 检查 `longterm` 是否定义了与项目 `AGENTS.md` 重复的代码风格和规则
- [ ] 如果有，删掉重复项，只保留项目事实与 session contract
- [ ] 检查 `longterm` 是否试图直接承担总司令派工逻辑
- [ ] 如果有，将其迁给 `AgentTeam`

### 剪枝后目标
`longterm` 只做**项目事实源**，成为唯一可信的长期项目状态层。

---

## 4.4 Orchestration Layer（`AgentTeam`）

### 应保留
- 总司令接手项目的方式
- 项目适配流程
- Agent 分工与派工模板
- ownership 管理
- 并行边界
- 回收结果、审阅、验收、上下文更新流程

### 应迁出 / 不应继续扩大
- 项目长期事实库
- feature 规格文档
- 执行技能方法论本体
- 项目级代码风格主规则

### 修剪动作
- [ ] 检查 `AgentTeam` 文档是否自己维护了一份项目事实模板
- [ ] 如果有，将其改为“读取 / 更新 longterm 工件”
- [ ] 检查 `AgentTeam` 是否在重复定义 `spec -> plan -> tasks`
- [ ] 如果有，改为“当 feature 开工时调用 spec规范”
- [ ] 检查 `AgentTeam` 是否在写会话执行技巧
- [ ] 如果有，引用 `superpower skill`，不要重写 skill 本体

### 剪枝后目标
`AgentTeam` 只负责**协作和调度**，不再变成第二个项目管理系统。

---

## 5. 五个必须消灭的重复区

### 重复区 1：多处维护项目规则
**现象：**
- `AGENTS`
- constitution
- longterm 文档
- spec 模板
- AgentTeam 文档
都在定义“项目规则”

**处理原则：**
- 项目规则只允许项目自己的 `AGENTS.md` / constitution 作为主定义
- 其他层统一改成引用

---

### 重复区 2：多处做任务拆分
**现象：**
- `longterm` 在拆项目
- `spec` 在拆 feature
- `skill` 在拆会话步骤
- `AgentTeam` 在拆派工

**处理原则：**
- 不是删除拆分，而是严格限定拆分层级
- 项目 / feature / 会话 / 派工 四种拆分不能混层

---

### 重复区 3：多处管理上下文
**现象：**
- 项目事实写在 longterm
- feature 上下文写在 spec
- 派工状态又写在 AgentTeam
- skill 里还混进了一些项目说明

**处理原则：**
- 长期事实 → `longterm`
- feature 事实 → `spec`
- 协作状态 → `AgentTeam`
- 会话临时推理 → `skill`

---

### 重复区 4：多处定义完成标准
**现象：**
- `skill` 说要验证
- `spec` 写验收标准
- `longterm` 写 passes
- `AgentTeam` 说要验收

**处理原则：**
- `skill` 定义验证纪律
- `spec` 定义 feature 验收标准
- `AgentTeam` 组织验收动作
- `longterm` 记录验收后的长期状态

---

### 重复区 5：多处维护项目导览
**现象：**
- 新项目接手说明可能同时出现在多个系统里

**处理原则：**
- 项目导览与接管流程由 `AgentTeam` 主导
- 项目事实材料从 `longterm` 读取
- `skill` 只告诉 Agent 接手时要先读什么，不维护项目导览正文

---

## 6. 迁移优先级
为了避免一上来大修，建议按下面顺序剪枝。

### Phase 1：先钉死主定义位置
优先做：
- [ ] 项目规则只认 `AGENTS.md` / constitution
- [ ] 项目事实只认 `longterm`
- [ ] feature 交付只认 `spec规范`
- [ ] 多 Agent 协作只认 `AgentTeam`
- [ ] `skill` 只认执行方法

目标：先解决“谁说了算”的问题。

### Phase 2：把重复内容改成引用
优先做：
- [ ] 把各层里重复出现的项目规则改成引用
- [ ] 把各层里重复出现的项目事实改成引用
- [ ] 把重复的 feature 管理逻辑收束到 `spec` 或 `longterm`

目标：先降低重复维护成本。

### Phase 3：删除无价值重复
优先做：
- [ ] 删除已经被主定义覆盖的重复文本
- [ ] 删除“历史遗留但没人真正依赖”的说明
- [ ] 删除只是换个说法重复一遍的流程段落

目标：让框架真正变轻。

### Phase 4：补接口文档
优先做：
- [ ] 写清楚 `AgentTeam` 怎么读 `longterm`
- [ ] 写清楚 `spec规范` 怎么消费项目事实
- [ ] 写清楚 `skill` 在什么地方停止，不越权

目标：把“靠理解协作”变成“靠接口协作”。

---

## 7. 新系统接入时的规则
将来如果再加入一个新系统，先问 5 个问题：

1. 它属于哪一层？
2. 它解决的是新问题，还是在重复已有层的职责？
3. 它是否维护新的项目事实？如果是，为什么不是 `longterm`？
4. 它是否定义新的 feature 交付流程？如果是，为什么不是 `spec规范`？
5. 它是否定义新的调度系统？如果是，为什么不是 `AgentTeam`？

如果回答不清楚，就不要接入。

---

## 8. 当前建议的最小整合心智模型
以后对任何项目，只记住下面四句话：

- **项目事实看 `longterm`**
- **feature 落地走 `spec规范`**
- **多 Agent 派工看 `AgentTeam`**
- **具体执行方法看 `superpower skill`**

如果一个内容同时想占两个位置，说明它还没被剪干净。

## 10. 一句话总结
剪枝不是“谁更强就删掉谁”，而是：

- 把每一层不该拥有的职责拿走
- 只让真正有最终职责的层保留主定义
- 其他层一律改为引用、消费、或协作

这样重叠才会变成配合，而不是内耗。
