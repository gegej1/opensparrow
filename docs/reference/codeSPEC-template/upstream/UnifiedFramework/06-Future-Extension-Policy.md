# Future Extension Policy

## 1. 目的
这份文档回答的问题是：

- 将来如果要引入新的记忆框架，怎么办？
- 将来如果要引入更成熟的多 Agent 架构，怎么办？
- 现在是否要提前预留？
- 如果预留，应该预留什么，不应该预留什么？

当前结论是：
**要预留扩展位，但不要预写具体实现。**

也就是说，我们现在应该提前定义：
- 扩展接入原则
- 扩展属于哪一层
- 扩展何时可以替换现有层
- 扩展何时只能作为增强层

但不应该现在就：
- 写死未来框架的目录结构
- 假设未来框架的具体接口
- 为尚未存在的系统制造大量空文件或空流程

---

## 2. 为什么需要现在就预留
如果完全不预留，等未来要接入新框架时，容易出现两类问题：

### 问题 1：重复建设
新框架一进来，很容易再长出一套平行规则、平行记忆层或平行调度层。

### 问题 2：错误接入
比如：
- 一个新的记忆框架接进来后，又维护了第二份项目事实库
- 一个新的多 Agent 架构接进来后，又维护了第二套 ownership 和派工规则

因此，**现在要预留的是“接入规则”和“决策框架”，不是未来具体实现本体。**

---

## 3. 应预留什么，不应预留什么

## 3.1 现在应该预留
### A. 扩展槽位（Extension Slots）
先定义未来新系统只能接入到哪一层：
- 记忆框架 → Project Memory Layer
- 多 Agent 架构 → Orchestration Layer
- 新 planning/spec 系统 → Feature Delivery Layer
- 新行为方法 / prompt / skill 系统 → Execution Layer

### B. 准入问题清单
任何新系统接入前，都必须先回答：
1. 它属于哪一层？
2. 它解决的是新问题，还是重复现有职责？
3. 它是替换当前层，还是增强当前层？
4. 它会不会制造第二份主定义？
5. 它的输入输出是否能接上现有接口？

### C. 替换规则
要先定义清楚：
- 什么情况下允许替换现有层
- 什么情况下只能作为外挂增强
- 替换后谁成为新的主定义

### D. 兼容期规则
未来引入新系统时，可能会有新旧双轨并存的一段时间。
现在就应该定义：
- 双轨期允许存在
- 但必须标注主从
- 双轨期结束后必须收敛到一个主定义

---

## 3.2 现在不应该预留
### A. 不要为未来框架先造空目录
例如：
- 不要现在就创建“未来记忆系统目录”
- 不要现在就写“未来多 Agent 架构配置文件”

### B. 不要先写死未来接口
未来的记忆框架或多 Agent 系统可能与你今天想的不一样。
现在写死具体接口，会让未来真正接入时反而受限。

### C. 不要让当前框架为了未来而变重
如果为了预留扩展，把当前最小内核搞得很复杂，就是过度设计。

---

## 4. 两种扩展类型

## 4.1 替换型扩展（Replacement）
定义：
新系统进入后，直接替换当前某一层的现有实现。

例如：
- 一个新的记忆框架成熟到足以替换 `longterm`
- 一个新的 spec 系统成熟到足以替换当前 `spec规范`

替换型扩展必须满足：
- 它完整覆盖当前层的核心职责
- 它不会制造第二份主定义
- 它能承接历史迁移
- 它能被统一框架中的其他层稳定消费

### 判断标准
如果新系统只能解决当前层的一部分问题，那它通常不应替换，只应增强。

---

## 4.2 增强型扩展（Augmentation）
定义：
新系统进入后，不替换当前层，只增强它的能力。

例如：
- 一个更成熟的多 Agent 调度系统，增强 `AgentTeam`
- 一个更智能的记忆辅助工具，辅助 `longterm`，但不替代主事实层

增强型扩展必须满足：
- 它不改变主定义归属
- 它不制造新的主数据库
- 它可以被移除，而不破坏主路径

### 判断标准
如果移除这个新系统后，项目仍然能沿当前主路径运行，它更可能是增强层。

---

## 5. 对未来“记忆框架”的策略

### 当前默认策略
未来若接入更成熟的记忆框架，默认先视为：
**Project Memory Layer 的候选增强或候选替代。**

### 接入前必须回答的问题
1. 它是否要替代 `longterm`，还是只增强 `longterm`？
2. 它是否维护项目画像、feature 全景、progress、init 这些核心事实？
3. 它是否会制造第二份项目事实源？
4. 它是否支持迁移已有 `longterm` 数据？
5. 其他层是否还能用同样方式读取项目事实？

### 当前建议
- 在没有明确证明它更好之前，先当作增强层
- 只有当它能够完整承接 `longterm` 的核心职责时，才考虑替换

### 一句话原则
**未来记忆框架可以更强，但项目事实主定义永远只能有一份。**

---

## 6. 对未来“多 Agent 架构”的策略

### 当前默认策略
未来若接入更成熟的多 Agent 架构，默认先视为：
**Orchestration Layer 的候选增强。**

### 接入前必须回答的问题
1. 它是否只是让派工更高效，还是要替换整个调度层？
2. 它是否会维护新的任务状态库？
3. 它是否会与现有 ownership 规则冲突？
4. 它是否能读取项目规则、项目事实、feature 规格，而不复制这些东西？
5. 如果去掉它，项目是否还能继续沿主路径工作？

### 当前建议
- 默认先当增强层，而不是替换层
- 只有当它能完整承担调度职责、且明显优于现有方式时，再考虑升级为新的调度主路径

### 一句话原则
**未来多 Agent 架构可以更强，但不应自己变成第二个项目事实层或第二个 spec 系统。**

---

## 7. 扩展接入的标准顺序
未来真的要接入新系统时，按这个顺序走：

### Step 1：先定位层级
先回答：它属于哪一层？

### Step 2：判断是替换还是增强
- 如果替换：必须证明能覆盖当前层核心职责
- 如果增强：必须证明不会制造第二主定义

### Step 3：跑接口检查
检查它能否：
- 读取现有主定义
- 不破坏现有闭环
- 与其他层通过最小接口协作

### Step 4：进入兼容期
在真实项目里做一段兼容期验证：
- 保留旧主路径
- 标注主从关系
- 记录风险与收益

### Step 5：做最终裁决
兼容期结束后，决定：
- 正式替换
- 保留为增强层
- 放弃接入

---

## 8. 兼容期规则
当未来新系统进入时，允许存在短期双轨，但必须遵守：

- 主定义只能有一个
- 旧系统与新系统必须标记主从
- 兼容期必须有明确结束条件
- 兼容期结束后必须收敛

### 兼容期结束条件建议
至少回答下面 4 个问题：
1. 新系统是否稳定？
2. 新系统是否确实减少了重复？
3. 新系统是否提高了效率或质量？
4. 新系统是否没有制造新的混层问题？

如果这 4 个问题答不清楚，就不要升级为主路径。

---

## 9. 决策模板
未来每次要接入新系统时，至少应做出一份简短决策记录，回答：

- 新系统名称：
- 所属层级：
- 类型：替换 / 增强
- 目标收益：
- 风险：
- 是否创建第二主定义：
- 是否需要兼容期：
- 兼容期结束条件：
- 最终裁决：

这份记录不一定要有固定文件名，但必须存在。

---

## 10. 当前建议
以我们现在的阶段来看：

- **应该现在预留扩展策略**
- **不应该现在预留未来实现**

换句话说：
- 预留“规则”是值得的
- 预留“空架子”通常是不值得的

这是因为：
- 规则能防止未来再次混层
- 空实现只会让当前框架变重

---

## 11. 一句话总结
未来一定可能接入更强的记忆框架或更成熟的多 Agent 架构。

现在最正确的做法不是“等到时候再说”，也不是“先把未来接口全写死”，而是：

- **现在先预留扩展策略和准入规则**
- **将来再按规则决定替换还是增强**

这样框架才既稳定，又有成长空间。
