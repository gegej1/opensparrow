# Migration Playbook

## 1. 目的
这份手册回答的是：
**一个已经在使用 `spec规范`、`longterm`、`superpower skill`，但边界还混在一起的项目，如何平滑迁移到统一框架。**

它不是面向全新项目，而是面向“已经跑起来，但有重复、重叠、口径漂移”的项目。

当前聚焦的迁移对象只有三件套：
- `spec规范`
- `longterm`
- `superpower skill`

`AgentTeam` 暂不作为迁移前提，只在项目已经明确需要多 Agent 调度时再叠加。

---

## 2. 迁移目标
迁移完成后，项目应达到下面 5 个状态：

1. 项目规则只有一个主定义来源
2. 项目长期事实只有一个主定义来源
3. feature 交付只走一套标准路径
4. `superpower skill` 只负责执行方法，不再承担项目事实或项目规则
5. 项目中任何一段流程都能说清楚：谁负责、谁不负责、写回哪里

---

## 3. 什么情况下说明项目需要迁移
出现以下任一情况，就说明项目已经适合开始迁移：

- 同一个项目规则在多个地方重复定义
- `spec` 文档里混入了大量项目长期状态描述
- `longterm` 文档里开始承担 feature 细任务拆分
- `superpower skill` 被当成项目数据库或长期记忆在用
- 团队经常搞不清“这件事到底该写到哪”
- 新人 / 新会话接手时要读很多重复文档才能开始工作

---

## 4. 迁移总原则

### 原则 1：先定主定义，再删重复
不要一上来就删除文档。
先确认：
- 项目规则主定义是谁
- 项目事实主定义是谁
- feature 交付主定义是谁
- 执行方法主定义是谁

然后再删重复项。

### 原则 2：先统一读写路径，再优化内容
如果接口还没统一，就先不要追求文案完美。
先让大家知道：
- 去哪读
- 去哪写
- 什么时候切层

### 原则 3：先迁主流程，不急着迁所有历史资产
优先迁移“当前还在用”的主路径。
对于历史旧文档，可以先标注为遗留，再逐步清理。

### 原则 4：迁移期间允许双轨短暂共存，但必须标注主从
在迁移期内，旧文档和新定义可能暂时同时存在。
但必须明确：
- 哪个是主定义
- 哪个只是兼容性遗留

---

## 5. 标准迁移顺序

## Phase 0：冻结判断标准
在开始迁移之前，先写清楚这 5 个判断：
- 项目规则由谁定义
- 项目事实由谁定义
- feature 交付由谁定义
- 执行方法由谁定义
- `AgentTeam` 在当前项目中是可选 overlay 还是尚未启用

这一步的目标是：
先让项目拥有“总框架裁决表”。

**最简裁决表应当是：**
- 项目规则 → 项目 `AGENTS.md` / constitution
- 项目事实 → `longterm`
- feature 交付 → `spec规范`
- 执行方法 → `superpower skill`
- 多 Agent 调度 → `AgentTeam`（若启用，仅作为 overlay）

---

## Phase 1：统一项目规则入口
### 要做什么
- 找出所有重复定义项目规则的地方
- 明确哪份 `AGENTS.md` / constitution 才是主定义
- 其他地方改为引用

### 典型重复点
- spec 模板里又写了一遍项目规则
- longterm 文档里又写了一遍代码风格
- 说明文档里又维护了一版禁改目录

### 完成标准
- 项目规则只剩一个主定义来源
- 其他层只说“遵循项目规则”

---

## Phase 2：统一项目事实入口（先做 `longterm`）
### 要做什么
- 确认 `app_spec` 是否能代表项目画像
- 确认 `feature_list` 是否能代表 backlog 主事实
- 确认 `progress` 是否能代表长期状态与会话记录
- 确认 `init` 是否能代表项目进入点

### 典型重复点
- 某些 README / spec 文档里长期维护项目状态摘要
- 派工说明或 prompt 模板里复制了一份当前项目事实
- 进度状态同时散落在多个手记里

### 迁移动作
- 保留 `longterm` 为项目事实主定义
- 将其他地方的项目事实改为：
  - 摘要引用
  - 链接到 `longterm`
  - 或直接删除

### 完成标准
- 新会话接手项目时，项目事实优先从 `longterm` 获取
- 其他地方不再维护平行版项目状态

---

## Phase 3：统一 feature 交付入口（再做 `spec规范`）
### 要做什么
- 明确所有非 trivial feature 一律走 `spec -> plan -> tasks`
- 检查项目里是否存在其他平行的 feature 交付方式
- 把平行方式收束到 `spec规范`

### 典型重复点
- longterm 里直接细拆 feature 执行步骤
- prompt 模板里直接替代 `plan` 和 `tasks`
- 某些 runbook 被当成 feature 规格使用

### 迁移动作
- 保留 `spec规范` 为 feature 交付主路径
- 让 `longterm` 只负责：
  - 选 feature
  - 记录完成状态
- 让 `spec` 只负责：
  - 定义这个 feature 怎么交付
- 为每个被选择的 feature 建立与 `spec` 目录或等价工件的唯一映射

### 完成标准
- 项目里不再存在第二套 feature 交付主流程

---

## Phase 4：收缩 `superpower skill` 到执行方法层
### 要做什么
- 检查 skill 相关说明中是否混入：
  - 项目长期状态
  - 项目规则主定义
  - feature backlog 主定义
- 把这些内容迁回各自应该在的层

### 正确保留的内容
- brainstorming
- planning
- debugging
- verification
- 其他会话执行技巧

### 迁移动作
- skill 只保留“当前会话如何做”
- skill 中如果需要项目事实，改为“先读 longterm”
- skill 中如果需要 feature 边界，改为“先读 spec”

### 完成标准
- `superpower skill` 不再承担项目长期记忆与项目规则主定义

---

## Phase 5：打通闭环
当以上四个阶段完成后，项目应能稳定走下面这条闭环：

`项目规则 -> longterm -> spec规范 -> superpower 执行 -> 写回 longterm`

如果项目启用了 `AgentTeam`，它应以 overlay 方式叠加在执行与验收环节，而不是改写这条主路径。

如果这条链能跑通，就说明迁移已经成功完成主路径。

---

## 6. 迁移时最常见的 6 个错误

### 错误 1：先删文档，后想边界
后果：
- 容易删掉仍在承担主定义的内容

正确做法：
- 先明确“谁是主定义”，再删

### 错误 2：试图一次性完成所有历史清理
后果：
- 迁移成本太高
- 容易影响当前正常开发

正确做法：
- 先统一主路径
- 再慢慢处理历史遗留

### 错误 3：把 `longterm` 也做成 feature 流程层
后果：
- 项目事实和 feature 交付混层

正确做法：
- `longterm` 只做项目事实层

### 错误 4：把 `spec` 写成项目说明书
后果：
- feature 文档越来越重
- 项目事实无法稳定回收

正确做法：
- `spec` 只负责这个 feature

### 错误 5：把 `superpower skill` 变成项目配置中心
后果：
- Agent 会越来越依赖隐式上下文
- 项目事实无法稳定落盘

正确做法：
- skill 只做执行方法

### 错误 6：在迁移期不标注主从
后果：
- 旧文档和新文档同时存在，但没人知道谁说了算

正确做法：
- 在迁移期明确标记：
  - 主定义
  - 遗留兼容
  - 待删除

---

## 7. 风险控制

### 风险 1：迁移打断当前项目开发节奏
控制方法：
- 迁移优先围绕当前主路径进行
- 不大面积修改无关历史文档

### 风险 2：旧文档仍被依赖
控制方法：
- 不直接硬删
- 先改成“遗留说明 + 指向主定义”

### 风险 3：团队继续沿用旧习惯
控制方法：
- 在统一框架文档里反复强调主定义位置
- 在项目接手和新 feature 开工时，强制走新主路径

### 风险 4：迁移后看似统一，实际上还是双轨
控制方法：
- 重点检查：项目规则、项目事实、feature 交付、执行方法这四类是否真的只剩一个主定义

---

## 8. 回滚策略
如果迁移进行到一半，发现影响太大，可以临时回到“主路径优先”策略：

1. 保留新确立的主定义边界
2. 停止继续删除旧文档
3. 把未完成迁移的内容标成遗留
4. 继续日常开发
5. 等下一轮再继续迁移

换句话说：
- 边界定义不回滚
- 清理动作可以暂停

---

## 9. 迁移完成的验收标准
只有下面这些条件同时成立，才算迁移真正完成：

- 项目规则主定义清楚
- 项目事实主定义清楚
- feature 交付主定义清楚
- `superpower skill` 不再越权
- `AgentTeam` 是否启用及其 overlay 身份清楚
- 新会话接手项目时，能在较少文档中快速进入状态
- 当前主线 feature 可以稳定按统一框架闭环推进
- `passes: true` 的写回已与对应 feature 的 acceptance evidence 建立握手

---

## 10. 迁移后的推荐状态
迁移完成后，一个项目的工作方式应尽量接近这样：

### 项目层
- 读 `AGENTS / constitution`
- 读 `longterm`

### feature 层
- 用 `spec规范` 定义 feature

### 执行层
- 用 `superpower skill` 控制执行纪律

### 协作增强层（可选）
- 如确实需要多 Agent 调度，再引入 `AgentTeam`

---

## 11. 一句话总结
迁移不是把所有旧东西删光，而是：

- 先统一主定义
- 再统一读写路径
- 再把重复内容改为引用或删除
- 最后让项目只保留一条稳定主路径

这才是从“混用框架”走向“统一框架”的正确方式。
