# F-019 Runbook - Commander Orchestration Governance

## 元数据
- 日期：`2026-04-09`
- 作者/Agent：`Commander`
- 关联 spec：`specs/013-commander-orchestration-governance/spec.md`

## 概述
- 本 runbook 将 OpenSparrow 当前会话的“总司令 + 固定 5 子 Agent + 可临时扩编”制度固化为长期执行 SOP。
- 目标不是替代每个 feature 的具体 spec，而是为后续所有 feature 提供统一的派工、审阅、收口与升级规则。
- 默认原则：总司令负责拆解、派工、审阅、集成和验收；主力实现尽量下放给子 Agent。

## 角色声明
- “总司令”是一个会话级职责角色，不固定绑定到某个历史 Agent、模型或供应商。
- 如果用户在新会话中重新指定新的总司令，则以用户最新指定为唯一有效口径。
- 历史 `claude-progress.txt`、旧 runbook、旧对话中出现过的“谁担任总司令”，只可作为背景参考，不得直接影响当前任务拆解、派工边界或权限判断。
- 当历史记录与当前用户指令冲突时，始终以当前用户指令为最高优先级。

## 固定编制（长期常备军）

### 1. `claudecodeA` - 前置拆解
- 主要职责：阅读需求、整理上下文、起草 `spec/plan/tasks`、明确验收标准与风险点。
- 适合任务：功能拆解、方案比较、任务单整理、验收口径收束。
- 不负责：大块运行时代码实现。
- 交付物：`specs/*` 文档、任务拆分说明、风险清单。

### 2. `codexA` - 核心实现
- 主要职责：承担主路径实现，优先处理核心逻辑、关键脚本、核心模块改动。
- 适合任务：`scripts/`、`ui/`、平台 wrapper/companion 的核心改动。
- 不负责：定义需求口径或修改长期治理文档。
- 交付物：代码变更、必要测试、实现摘要。

### 3. `codexB` - 次路径实现
- 主要职责：处理与主路径相邻但边界清晰的独立模块，分担多线实现压力。
- 适合任务：与 `codexA` 并行的相邻模块、适配层、脚本同步、次要页面或配套逻辑。
- 不负责：与 `codexA` 同时修改同一文件集。
- 交付物：独立模块改动、对应验证说明。

### 4. `codexC` - 验证与回归
- 主要职责：复现问题、运行定向验证、做边界测试、补 smoke / 语法检查、确认回归风险。
- 适合任务：`bash -n`、`node --check`、隔离 smoke、复现 bug、检查打包/服务差异。
- 不负责：定义新需求或大块文档规划。
- 交付物：验证结果、失败复现路径、边界风险清单。

### 5. `claudecodeB` - 收口与交付
- 主要职责：更新 `docs/`、`runbooks/`、`feature_list.json`、`claude-progress.txt`，整理发布/交付说明。
- 适合任务：runbook、handoff、文档口径统一、长期记录同步。
- 不负责：主力代码实现。
- 交付物：使用文档、runbook、longrun 记录、交付摘要。

## 总司令职责边界
- 默认负责：需求拆解、任务优先级、派工、文件所有权分配、结果审阅、集成决策、最终验收。
- 默认不负责：主力实现与长时间代码开发。
- 例外介入条件：
  - 多 Agent 结果冲突；
  - 关键集成收尾需要统一裁决；
  - 同一问题经过两轮派工仍未解决；
  - 任务本身无法再合理切分。

## 默认派工模式

### A. 小任务
- 默认编队：`claudecodeA + 1 codex + codexC`
- 适用：单线修复、单模块改动、单文档 feature、窄范围验证
- 总司令动作：快速拆解 → 指定一个实现 Agent → 指定一个验证 Agent → 审核结果 → 收口

### B. 中任务
- 默认编队：`claudecodeA + codexA + codexB + codexC + claudecodeB`
- 适用：双线实现、代码与文档并行、需要回归与 longrun 同步的 feature
- 总司令动作：拆成 2 条独立实现线 → 分配验证 → 要求收口员同步 runbook / longrun

### C. 多线战役
- 默认编队：沿用中任务编队，并视需要临时扩编 1–3 人
- 适用：多模块同时推进、涉及平台兼容 + 代码实现 + 文档收口 + 回归验证
- 总司令动作：先划分战区，再为每个战区派唯一 owner，最后统一集成

## 临时扩编规则

### 触发条件
- 同时存在 3 条以上独立实现线
- 需要单独的只读侦察或历史比对
- 大量文档/迁移/交付说明需要与实现并行
- 一个需求同时包含实现、验证、审阅、发布收口多条链路

### 推荐临时角色
- `codexScout`：只读侦察，查代码路径、依赖关系、历史提交，不写代码
- `codexFix`：专修一个独立 bug 或一个独立模块
- `codexVerify`：只做测试、语法检查、smoke 与回归
- `claudecodePlanner`：处理大任务拆解、子任务包与执行顺序
- `claudecodeReviewer`：复核文档口径、验收项与交付说明

### 编制原则
- 固定 5 人是常备军，临时 Agent 是项目制特遣队
- 临时 Agent 任务完成后即撤，不形成长期常备职责
- 扩编时仍必须遵守文件所有权与并行改动边界

## Cloud Code / CodeX 分工原则
- `Cloud Code`：偏规划、文档、验收口径、任务拆解、成果整理
- `CodeX`：偏实现、调试、测试、验证、脚本与代码修复
- 除非总司令明确指定，否则 `Cloud Code` 不接大块代码实现，`CodeX` 不定义需求口径

## 冲突规避规则
- 派工前必须声明每个 Agent 的文件所有权范围
- 两个实现 Agent 不同时修改同一文件集
- 验证 Agent 只补验证所需最小改动，不擅自扩大实现范围
- 收口 Agent 不重写实现逻辑，只同步文档与长期记录
- 子 Agent 返回结果后，总司令先审再集成，不直接无脑合并
- 同一问题若连续两轮派工仍未解，总司令必须升级处理：重新拆分、换 Agent 或亲自接管关键决策

## 任务派单模板

### 模板 1：实现 Agent
- 任务目标：一句话说明本次需要实现什么
- 文件范围：列出允许修改的文件路径
- 约束：不得修改的目录或文件、不可越界的职责
- 验证：必须跑的最小验证命令
- 返回格式：改了哪些文件、为什么这么改、验证结果如何

### 模板 2：验证 Agent
- 待验证对象：实现 Agent 产出的文件或行为
- 验证命令：精确命令或复现步骤
- 风险检查：边界条件、回归点、未覆盖项
- 返回格式：PASS / FAIL、证据、剩余风险

### 模板 3：收口 Agent
- 同步对象：`docs/`、`runbooks/`、`feature_list.json`、`claude-progress.txt`
- 目标：把本轮 feature 的落盘记录补齐
- 返回格式：更新了哪些记录、记录口径是否与实现一致

## 总司令 SOP

### 开工前
- 阅读 `AGENTS.md`、相关 spec / longrun / runbook
- 判断任务属于小任务、中任务还是多线战役
- 明确文件边界、风险点、验收标准与是否需要扩编

### 执行中
- 只做调度、澄清、审阅与集成决策
- 追踪每个 Agent 的责任边界与状态
- 对冲突及时裁决，不让多个 Agent 长时间编辑同一区域

### 收尾时
- 要求 `codexC` 或等价验证角色给出验证证据
- 要求 `claudecodeB` 或等价收口角色同步 longrun / docs
- 检查 spec、runbook、feature list、progress 是否一致

## 每轮任务完成后的必做同步
- 若任务非 trivial，先补 `specs/<feature>/spec.md` → `plan.md` → `tasks.md`
- 完成后至少同步：
  - `longrun/workspaces/opensparrow-unified/feature_list.json`
  - `longrun/workspaces/opensparrow-unified/claude-progress.txt`
  - 受影响的 `docs/`、平台指南或 runbook
- Shell / `.command` 变更优先 `bash -n`
- PowerShell 变更如环境可用则补 `pwsh` 语法解析或 dry-run 说明

## 后续执行建议
- 后续新任务默认按本 runbook 派工，除非用户另行指定
- 若出现新的高频角色，再评估是否从“临时特遣队”升级为固定编制
- 若实际执行中发现某职责边界长期失衡，应先改本 runbook，再改具体 feature 的工作方式
