# F-019 Runbook - Commander Orchestration Governance

## 元数据
- 日期：`2026-04-09`
- 作者/Agent：`Commander`
- 关联 spec：`specs/013-commander-orchestration/spec.md`

## 概述
- 本 runbook 用于定义 OpenSparrow 项目后续默认执行制度：`总司令 + 固定 5 子 Agent + 可临时扩编`。
- 目标不是取代现有文档驱动流程，而是在 `spec -> plan -> tasks -> 实现 -> 验收 -> longrun` 这条链路上，明确谁负责什么、什么时候扩编、如何避免并行冲突。
- 该制度属于项目执行治理，不直接修改运行时代码行为。

## 固定编制（常备 5 人）

### 1. `claudecodeA` — 前置拆解
- 负责把需求转成 `spec/plan/tasks`、验收标准、风险点与边界约束。
- 负责在任务开始前把“什么算完成”写清楚。
- 默认不承担大块运行时代码实现。

### 2. `codexA` — 核心实现轨
- 负责主路径代码改动，优先承担本轮最核心、最直接的实现任务。
- 适合 `scripts/`、`ui/`、平台脚本或关键逻辑修复。
- 同一轮并行中，不与 `codexB` 修改同一文件集。

### 3. `codexB` — 次路径实现轨
- 负责与主路径相邻但独立的实现任务。
- 常用于把大 feature 拆成两个可并行子任务，例如“主逻辑”与“配套入口/兼容层”。
- 与 `codexA` 同样默认不负责定义需求口径。

### 4. `codexC` — 验证轨
- 负责复现、语法检查、smoke、回归验证、边界案例检查。
- 默认优先做“验证、证伪、找缺口”，而不是先写代码。
- 若发现根因与预期不一致，应把问题回抛给总司令重新拆解或改派。

### 5. `claudecodeB` — 收口轨
- 负责更新 `docs/`、`feature_list.json`、`claude-progress.txt`、runbook、发布说明等长期记录。
- 负责把“完成了什么、怎么验证的、还剩什么风险”写清楚。
- 默认不承担主实现，但可以整理对外交付文案。

## 总司令职责边界

### 总司令负责
- 判断任务规模：小任务 / 中任务 / 多线战役
- 设计编队：固定编制 or 临时扩编
- 派单、控边界、审结果、做最终集成判断
- 在子 Agent 结果冲突时做裁决
- 在完成前确认验证证据、收口质量与对外汇报口径

### 总司令不默认负责
- 不作为主力实现者直接承担绝大多数代码开发
- 不在没有 spec / plan / tasks 的情况下越过文档流程直接改运行时代码
- 不把最终验收责任下放给任一单独子 Agent

### 升级接管条件
- 两轮子 Agent 迭代后问题仍未解决
- 出现多 Agent 冲突，且需要统一重构/回收改动
- 涉及跨模块集成判断，单个子 Agent 无法独立拍板

## 临时扩编规则

### 什么时候扩编
- 同时存在 3 条及以上独立代码线要并行推进
- 需要专人做“只读侦察”，避免实现者先入为主
- 文档、发布、迁移说明与代码改动需要并行推进
- 一个任务同时包含“实现 + 验证 + 文档收口 + 平台兼容”四类工作

### 常见临时角色
- `codexScout`：只读侦察，负责代码路径、依赖链、历史提交、影响面分析
- `codexFix`：专修一个独立 bug 或一个独立模块
- `codexVerify`：只做测试、脚本校验、smoke、回归
- `claudecodePlanner`：专门拆大任务、整理子任务包
- `claudecodeReviewer`：专门审文档口径、验收项与交付说明

### 撤编原则
- 临时 Agent 只按项目制存在
- 所属子任务结束、结果被总司令吸收后即撤编
- 不保留“长期模糊职责”的临时角色

## 默认派单模型

### 小任务
- 编队：`claudecodeA + 1 个 codex + codexC`
- 适用：单文件修复、小范围脚本修改、单点验证
- 目标：快速完成，不为小改动引入过多调度成本

### 中任务
- 编队：`claudecodeA + codexA + codexB + codexC + claudecodeB`
- 适用：一个 feature 里有 2 条独立实现线，并需要同步文档与回归
- 目标：实现、验证、收口并行推进

### 多线战役
- 编队：在“中任务”基础上临时扩编 `Scout / Reviewer / Planner / Verify`
- 适用：跨模块、多平台、长链路任务
- 目标：把侦察、实现、验证、收口拆成可并行战区，由总司令集中协调

## 冲突规避规则
- 同一轮并行中，两个 `CodeX` 不改同一文件集
- 同一功能只允许一个“主实现者”，其他 Agent 只能辅助验证或补文档
- `Cloud Code` 默认不接大块实现，专注拆解、审阅、文档与收口
- 子 Agent 不得擅自回滚其他 Agent 的修改；若发现冲突，先回报总司令
- 涉及 longrun / runbook / feature list 的最终总装由总司令或收口轨统一完成

## 验收与收口 SOP

### 1. 接单
- 总司令先判断任务是否需要先补 `spec/plan/tasks`
- 如果任务非 trivial，则必须先落文档，再进入实现派单

### 2. 分级
- 判断是小任务、中任务还是多线战役
- 识别是否存在独立问题域，决定是否并行派工

### 3. 派工
- 给每个子 Agent 一个明确边界：目标、文件范围、禁止项、回报格式
- 同轮并行任务之间必须先分开文件集，再开工

### 4. 中途回收
- 若子 Agent 报 `BLOCKED`、`NEEDS_CONTEXT` 或连续两轮未解决，总司令必须重新拆解或改派
- 若发现 plan 本身有问题，总司令优先修正文档口径，再继续执行

### 5. 验证
- `codexC` 或临时 `codexVerify` 负责提供验证证据
- 总司令在对外宣告完成前必须亲自检查验证输出，不得只凭子 Agent 口头报告

### 6. 收口
- `claudecodeB` 负责更新 runbook、`feature_list.json`、`claude-progress.txt` 与相关说明文档
- 总司令负责最终对外摘要：做了什么、没做什么、证据是什么、风险还剩什么

## 与仓库规则的关系
- 本制度服从 `AGENTS.md` 与 `.specify/memory/constitution.md`
- 文档驱动优先级不变：非 trivial 任务先有 `spec -> plan -> tasks`
- `vendor/`、冻结目录、平台入口脚本差异等现有边界不因本制度改变

## 推荐使用方式
- 把本 runbook 视为“任务执行编队手册”
- 每次新任务开始前，先决定是否需要引用本制度进行编队
- 每次 feature 完成后，确认 longrun 记录是否已经同步，否则视为未真正收口
